# D-0010 — Evidence sets and versioned observer ownership qualification

**Status:** PROPOSED — pending independent re-review.
**Affects:** SPEC §5.2, §5.5, §6.1, §7.3, §9.3, §11.4; D-0005 (reload rule), D-0007 §6 and §10; MILESTONES M2 exit gate.

## Context

D-0007 §10 left three canonical fields as the latest arrival: an execution's attach mode and presence, the human-follow-up frontier, and a session's observer link state. M2's producers (the observer mod, the companion's ordered inventory, conventional hooks beside the mod) can emit competing valid observations of each, so last-arrival-wins would make canonical state depend on delivery order. The same review found two more arrival-dependent values on the follow-up path: an input's origin, submission point and active turn were each overwritten by every submission report, and the frontier only ever advanced, so an acceptance followed by a rejection left it advanced while the reverse order did not.

D-0005 requires that a reloaded observer's session identity, learned through the interceptable `$.session.id()`, stays lower-tier until separate native proof restores authority, and that nothing is reattributed to the currently active session.

## Decisions

1. **Explicit reducer versions.** The first M2 candidate introduced reducer 3 for the evidence sets below. F1B remediation changes its persisted ownership proof representation and authority predicate, so the current proposal is `REDUCER_VERSION = 4`, with an explicit upgrade from existing reducer-3 development stores. New canonical facts carry payload version 2. Every current canonical observation also carries admission payload version 2 in the existing durable `observations.payload_version` column, exposed as `JournalEntry.payloadVersion`, including observations whose normalizer produces no facts. Retained version-1 headers and facts remain unchanged. The observation header identifies the historical prefix for versioned replay; no derived database metadata becomes a second source of truth. Missing fields in earlier serialized journal entries default to version 1; invalid or future stored header versions refuse recovery.

2. **Evidence sets.** Each report is kept as an observation with its observation ID, fact index, causal point and provenance:
   - `ExecutionRecord.attachments` (attach mode, presence, runtime ID, device);
   - `SessionRecord.links` (link state, provider process, whether the observer's profile is qualified and its version);
   - `InputRecord.submissions` (origin, original submission point, active turn).

   The displayed value is derived each pass from the reports no other report causally follows (`causal::compare`). When those disagree the result is conservative and flagged: the lowest execution mode, the least live presence (`DETACHED > PARKED > LIVE`), no runtime ID or device, an `UNCLASSIFIED` origin (which never qualifies a follow-up), and the most degraded link (`DISCONNECTED > CONFLICT > STALE > UNKNOWN > CURRENT`). `attachmentConflict` and `linkConflict` make the disagreement visible. A record with no report keeps the value an M0 baseline gave it; any report supersedes that value, since the baseline precedes every journal fact.

3. **The frontier is re-derived, not advanced.** A session's frontiers are recomputed from every input it holds whenever one changes: one per (actor, order domain) of the inputs with verified accepted human provenance and no rejection. A late rejection withdraws what an earlier acceptance advanced, and a frontier no input supports is removed.

4. **Host-read lifecycle evidence, corrected by F1B.** A fact's provenance can be `HOST_READ`: a qualified provider outcome whose original Session ownership rests on a middleware-interceptable host read. It is retained in `TurnRecord.pendingOutcomes`. A historical execution attachment, even for the same ProcessKey, does not authorize it. The rejected candidate's attachment predicate was insufficient when process P changed from Session A to B and a reload host read still claimed A.

   A current helper performs two fresh native inventory reads and kernel samples, checking its actual provider parent's ProcessKey incarnation and executable identity against the claimed Session. Only after that join succeeds does the helper generate a token and independently commit or durably spool `ObserverOwnershipCorroborated`. The returned token is only a correlation reference; middleware returning a fabricated token cannot create the separate proof fact. The proof is scoped by provider namespace, Session, ProcessKey, exact executable identity, observer source epoch and ownership generation.

   The observer seals a returned token only if its original immutable Session scope is unchanged. A qualified core `TurnStarted` must capture that sealed scope, and the outcome must retain the same scope. The reducer requires the causal chain **seal before original Turn start before outcome**, plus the separately admitted exact proof. Proof, seal and outcome may arrive in any delivery order; their source causal points and immutable identities determine authority. Pre-seal Turns remain pending even when a later proof exists. A later A interval cannot retrofit a proof into an original A interval. An outcome from another process incarnation, executable, source epoch, ownership generation or token remains pending.

   The evidence sets now include `SessionRecord.ownershipProofs`, ownership scope on seal link observations and pending outcomes, and `TurnRecord.ownershipStarts`. These authority-bearing fields appear in the semantic oracle. The session's `observerTier` is `NATIVE` for qualified engine-stamped identity, `RESTORED` for a separately proven and sealed host-read scope, and `LOWER_TIER` otherwise. An unqualified profile emits no lifecycle outcome. Neither plugin-origin lifecycle dispatch nor an interceptable host-list or spawn result becomes native authority.

5. **Upgrade from reducers 1 and 2.**
   - A checkpoint written before reducer 3 holds derived values, not the reports they came from. Before the existing upgrade, every fact at or before the checkpoint's cursor is read back into the sets through the same `record_evidence` the reducer uses, so the sets equal what reducing those facts records.
   - After the re-derivation, a record whose materialized row the upgrade left as committed keeps its committed revision. One whose row it changed takes the upgrade's cursor.
   - The upgraded state is therefore the same, to the state hash, wherever the earlier checkpoint sits. Attention and outbox keep D-0007 §6's handling; a binding keeps its proof revision.
   - A link report written before reducer 3 is read as reducer 2 treated every report: qualified.

6. **The mod's `session.attach`/`detach` is not an execution attach.** It has no activation identity, so mapping it onto `ExecutionAttached` would create a second execution per Session and turn exact Returns into `MULTIPLE_ATTACHMENTS` refusals. It stays journaled metadata.

7. **Reducer 3 → 4 is an explicit retained-fact upgrade.** The old checkpoint and its version-1 suffix are first recovered under the historical rule so committed owner decisions and attention history remain recoverable at every checkpoint position. The upgrade then reads the retained canonical facts, withdraws uncorroborated host-read outcomes, and re-derives authority under reducer 4 using catch-up delivery. A pending claim missing its retained canonical fact refuses the upgrade; a derived completion flag is not a substitute. Direct native outcome facts survive even when they report the same enum value as a withdrawn host-read claim.

   Historical attention and its committed owner-command facts/receipts stay auditable. An output no longer supported by qualified evidence receives the explicit `EVIDENCE_UNAVAILABLE` resolution cause; any owner resolution remains alongside it. Its unsent intent becomes suppressed. Already committed notification dispositions for unaffected native output remain unchanged, and eligibility first discovered during an upgrade is held. A genuine later output removes only the evidence-unavailable cause and cannot erase an owner decision.

   Genesis replay reconstructs every version-1 historical prefix, then applies the same explicit transition. A native-only prefix also requires that transition even when no host-read authority is withdrawn. The first version-2 observation header permanently selects the new authority rules; a later delivered version-1 entry cannot revive the historical predicate. A zero-fact metadata observation fixes this boundary just as a fact-bearing observation does. A store upgraded before receiving any new observations replays the same transition at its retained endpoint; later metadata cannot relocate it. Recovery from a valid older checkpoint with a mixed-version suffix applies the transition at that same first version-2 header, then replays the current suffix. Process and execution revisions, whose materialized tables have no revision column, take the transition cursor in both upgrade and versioned replay. Checkpoint position does not change canonical truth or the exact resulting checkpoint hash.

## Consequences

- Equivalent admissible histories converge in the semantic projection (which now includes the conflict flags, the observer tier and pending outcomes). Exact replay, checkpoint-plus-suffix replay and restart reproduce the full state hash. Arrival-ordered bookkeeping (revisions, created cursors) is excluded from cross-order comparison as D-0007 §3 states.
- An upgraded reducer-2 store can resolve differently from reducer 2 where reducer 2 depended on arrival order. The reducer-2 fixtures (`fixtures/m2/reducer-2-store`) record such cases: a rejected follow-up no longer resolves the earlier output, and its suppressed intent re-arms HELD, never live.
- Production stays on reducer 2 until M2 is accepted. Deploying an M2 build upgrades a store irreversibly for reducer-2 builds, so it follows the controlled backup/rehearsal procedure used for reducer 2.

## F1B remediation qualification status

`evidence/M2/remediation-1/f1b/` records the actual rejected-source counterexample, two genuine reducer-3 stores generated by that source, and focused portable adapter/SQLite evidence. The first store includes historical A/P and current B/P attachments, falsely handled and unhandled outputs, a durable owner command, and an independent native control. Checkpoints at cursors 0, 2 and 11 test the same retained history through the production upgrade path. The second store contains only native authority and checks the explicit transition at cursors 0, 2 and 7. Both test zero-fact metadata tails, checkpoint/restart before a new fact, the later first current fact, and recovery from an older verified checkpoint with the same mixed-version suffix. That suffix also includes an actual production-admitted notification disposition and owner Resolve command; their full timestamps, revisions, attention, outbox and stable retry receipts must survive. Preserved failures show why a fact-only transition marker was insufficient. The proof/seal/start/outcome test enumerates all 24 delivery orders, including stable-UUID retries, with wrong-incarnation/image/scope controls and the actual F1A TypeScript captures.

This is a proposed remediation, not independent acceptance. The former 819 ms native `RESTORED` readback qualified only the rejected historical-attachment predicate. A new source-matched macOS unchanged-ID reload/new-Turn smoke must qualify the independent native proof producer and current end-to-end path. Linux portable execution must not be described as native macOS execution; absence of that new native smoke remains an explicit qualification gap.
