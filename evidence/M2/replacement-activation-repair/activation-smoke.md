# Future activation-only gate — design, not execution

Status: **UNVERIFIED / NOT AUTHORIZED IN THIS UNIT**. Independent review of this source candidate precedes authorization to prepare and launch this smoke. This document supplies requirements, not an implemented harness or a runnable experiment.

The smoke must distinguish initialization, discovery, registration and execution. A returned initializer response alone cannot pass any later stage. No inference or user prompt is required. Preserve the existing headless initialization mechanism; do not invent an extra user event to make the callback run.

## Preconditions and separation from calibration

1. Verify the exact Claude Code 2.1.295 executable/hash, reviewed two-plugin source hashes, unchanged canonical observer bytes, supported declarations and loading interface. Freeze fresh smoke/run/plugin/configuration identities. Never reuse any consumed conformance run, runtime, epoch, incarnation, challenge or manifest as new evidence.
2. Review a narrowly scoped, qualification-only activation entry and output collector before execution authorization. The current positive probe automatically starts the timing grid when its callback runs; launching that probe would not be an activation-only smoke. This unit deliberately adds no activation switch or replacement callback. A future activation entry must contain no clock samples, background work, seven-delay grid or conformance markers. Its source difference from the positive probe must be explicit and reviewed, and its success must not be promoted to evidence that the positive timing task completed.
3. Use the installed loader's separately supported inspection/validation path to admit the **exact repaired timing module** without executing its callback. Record the original observer and exact timing handler registration graph. Separately launch the reviewed activation-only entry for callback and forwarding witnesses. If the installed interface cannot safely separate admission from callback execution, stop that gate with the precise limitation. Do not invoke the positive timing callback to work around it.
4. Inspect and verify a supported host-side diagnostic collection mechanism before relying on it. Persist discovery and registration/admission results outside the callback, so a failure before module evaluation is visible. A private debug log or a loader-owned structured registration result may support this only after its exact installed interface is verified. Do not assume that a debug flag exposes a registration inventory.
5. Use only private disposable settings and roots, exactly one loading mechanism and two distinct names. Keep strict empty MCP, default observer capture delivery disabled and all owner settings untouched. Freeze the expected non-built-in plugin inventory; any unrelated non-built-in plugin is a failed isolation gate. Record managed/built-in contributors separately.
6. A separately reviewed readiness exchange may use the same supported Unix-socket HTTP API with a fresh nonce and an owned, non-measuring readiness endpoint. It must not call the conformance marker endpoint, generate a native timing sample or reuse a challenge plan. The existing timestamp responder has no such activation endpoint; a future readiness fixture requires its own narrow review and authorization. No responder or readiness fixture is implemented or executed here.
7. Use independently verified kernel image, UID, parent and PID-birth ownership before any signal. Retain the fixed 20-second external deadline. A missing stage or output is a failure, followed by verified cleanup only of owned disposable children. No deadline extension, owner process action, production settings change or implicit conformance retry is permitted.

## Required independent stage outputs

| Stage | Required witness | Insufficient evidence |
|---|---|---|
| Process/initializer | Exact kernel image/birth identity and original initialization response | Provider output without owned process attribution |
| Discovery | Loader-owned resolved roots, names, manifest hashes and complete allowed plugin inventory | Two directories merely existing on disk |
| Registration | Loader-owned admission or rejection, module identities and one unmatched session.start per separate plugin | Initializer acknowledgement or source-only hook counts |
| Original observer | Exact canonical observer registration admission; host dispatch/continuation witness identifies the observer handler | Enabling capture delivery or changing canonical observer bytes |
| Exact timing handler | Admission of the exact reviewed timing module through a supported non-executing loader path | Admission of an activation-only surrogate relabeled as the positive module |
| Callback entry | Fresh source-bound activation entry record correlated with host dispatch | A catch handler or stale output file alone |
| Forwarding | Host continuation and downstream completion identify the unchanged observer and activation chain, with exactly one next(e) per handler | Assuming execution order from plugin argument order |
| Persistence | Readback of the fresh callback-output bytes/hash, matching smoke nonce and callback identity | Successful file creation without readback |
| HTTP readiness | Native independent receipt/response and mod readback match the fresh readiness nonce over the private socket | Clock calibration, requested delays or initializer response |
| Termination | Bounded stage outcomes and independently verified owned cleanup | Missing output or silent provider/responder exit |

The production observer stays unchanged. If supported host dispatch witnesses cannot attribute its callback/continuation while capture is disabled, that subgate remains blocked; an activation surrogate cannot prove the original observer executed. Callback output contains only readiness/activation telemetry and never provider history or inference. The harness reads it back without mutating owner resources.

## Required cases and discriminating outcomes

| Case | Required recorded outcome |
|---|---|
| Intentional original duplicate | Loader rejects the frozen same-plugin duplicate before module evaluation; retain exact refusal and zero callback witness |
| Corrected two-plugin composition | Both distinct roots discovered and admitted; original observer and reviewed activation entry dispatch/forward; fresh output read back; owned HTTP readiness succeeds |
| Registration failure before evaluation | Host-side rejection with stage/module identity; no callback witness; independently distinguish from provider initialization alone |
| Callback execution failure | Registration succeeds, host dispatch is observed, callback failure is recorded separately, output/readiness completion is absent |
| Output-write failure | Registration and callback entry independently observed; write/readback stage fails; preserve controller outcome even when callback cannot persist its own error |
| Initialization without callback evidence | Initializer stage succeeds; later stages remain missing/failed at the external deadline; never label activation PASS |

Fault cases use only disposable files/configuration. Register/dispatch diagnostics must be collected outside a callback-level catch. A controller-owned stage record must survive missing callback output and record exact stage, source, nonce, deadline and cleanup outcomes. Native logs stay private until classified; only scoped hashes, stage results and sanitized owned identities are publishable.

Passing this future smoke would establish only its stated activation/readiness scope. A new positive conformance remains separately authorized, newly source-frozen and independently identified. No full F4 campaign, compact helper experiment, application deployment, M2 merge or M3 follows automatically.
