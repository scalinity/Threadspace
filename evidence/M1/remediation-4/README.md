# M1 remediation of the fourth independent review

The fourth independent review of candidate `579df5b7902396f706095a28b455f9189513daa5` accepted the six request-level outbox dispositions of the reducer-1 upgrade (1 PENDING / 4 HELD / 1 SUPPRESSED) and every other M1 group. It found one remaining blocker: the upgrade's rebase (`keep_committed`) restored an attention item's committed revision but not its nullable committed `resolved_at_ms`. So identical reducer-1 histories could upgrade to different durable states depending on where reducer 1's newest checkpoint sat.

This is a resolved-at timestamp rebase repair. The reducer, the notification lifecycle and the accepted catch-up replay, decision conversion and outbox rebase are unchanged.

## The defect

The six-entry history:

| Cursor | Entry | Captured wall time |
| ---: | --- | ---: |
| 1 | `session.start` | `1791000000010` |
| 2 | `turn.start` t1 | `1791000000020` |
| 3 | INPUT positive P3, sequence 3 | `1791000000030` |
| 4 | Owner Resolve covering P3 | `1791000000040` |
| 5 | Uncovered INPUT positive P4, sequence 4 | `1791000000050` |
| 6 | Comparable clear C5, sequence 5 | `1791000000060` |

Reducer 1 kept item `663fb032-fef5-812b-9104-b15bd1135349` resolved through P4 and committed `resolved_at_ms = 1791000000040`, the owner's time.

**How placement changed the result.** Reducer 2 replays any entries after reducer 1's newest checkpoint. When the replay covers cursors 5 and 6:
- P4 reopens the item, which clears its resolution time;
- C5 resolves it again, at `1791000000060`;
- the rebase restored the item's revision but left that time in place;
- the upgrade's re-derivation keeps an existing resolution time (`get_or_insert`), so `1791000000060` was materialized, checkpointed, and reproduced on every restart.

With the checkpoint at cursor 6 nothing is replayed, and the item keeps `1791000000040`.

The semantic hash is the same in all three, since semantic equality does not distinguish the two times; the per-path comparison and the asserted value are what detect the defect.

## Repair (`7fe5539`)

**What the rebase now does.** For each attention item with a committed `attention_items` row, `keep_committed` reads `resolved_at_ms` before it compares the rebuilt row with the committed one:
- `Sql::Null` is read as `None`;
- `Sql::Integer(t)` is read as `Some(t)`;
- any other type, or a missing column, refuses the open with `JournalError::Invalid { detail: "committed attention row <id>" }`. Nothing is substituted.

**Items with no committed row.** An item reducer 2 derived first has no row. It keeps the time its recovery derived, and no historical time is invented for it.

**Current evidence still decides.** The restoration happens before `Engine::upgrade`, so the re-derivation remains authoritative:
- an item still resolved keeps the restored time;
- an item reducer 2 finds unresolved has its time cleared (`derive_attention_resolution`, unchanged).

Resolution causes, owner state, eligibility and outbox disposition are all still derived from current evidence.

The decode is `nullable_integer`, unit-tested in `canonical::tests`.

## Malformed committed time

`attention_items` is a STRICT table, so SQLite itself refuses a non-integer `resolved_at_ms`. `a_malformed_committed_resolution_time_refuses_the_upgrade` therefore makes disposable copies whose table definition has lost `STRICT` (through `writable_schema`), writes a TEXT, a REAL and a BLOB value in turn, and opens each with `Journal::open_with`.

In each case the open fails with `JournalError::Invalid { detail: "committed attention row 663fb032-…" }`, and afterwards:
- the checkpoints are unchanged, still reducer 1's 0, 4 and 6, with no `REDUCER_UPGRADE`;
- every other row is byte-for-byte unchanged (same history SHA-256).

## Atomicity and restart

**Transaction.** The rebase runs in memory inside `load_engine`, on the one writer connection, before `persist_upgrade` opens its immediate transaction. That transaction writes every materialized row, the restored time included, together with the `REDUCER_UPGRADE` checkpoint.

**Proven precommit failure.** The malformed-time refusal is raised in `load_engine`, before that transaction. The test shows the store's rows and reducer-1 checkpoints unchanged afterwards.

**Not separately injected.** No crash point exists inside the upgrade transaction (the qualification crash points are on the admission path). A failure inside it rests on SQLite's transaction rollback; it was not injected separately here.

**Restart.** `REDUCER_VERSION` stays 2 and `upgrade_json` is unchanged. In every variant there is exactly one `REDUCER_UPGRADE` checkpoint, and a restart reproduces the state without writing another.
